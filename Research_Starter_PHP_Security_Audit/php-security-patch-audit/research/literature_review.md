# 2. Literature Review

## 2.1 Introduction

The use of large language models (LLMs) in software development has expanded beyond code completion. Current coding assistants can inspect source files, explain code, suggest changes and generate tests. These capabilities are particularly relevant to software security, where understanding why a defect occurs is often as important as identifying the affected code. A useful security assistant should be able to explain the conditions that cause a vulnerability and help produce tests that distinguish vulnerable behaviour from corrected behaviour.

However, producing a convincing explanation or a test that runs successfully does not necessarily mean that the underlying problem has been understood. An explanation may describe the wrong cause, while a generated test may simply reproduce the behaviour of the vulnerable program. This review examines research on LLM-based vulnerability analysis, code explanations, regression-test generation and the evaluation of AI agents on real software security tasks. The purpose is to identify what has already been established and to determine where the present study can make a focused contribution.

## 2.2 LLMs for vulnerability identification and root-cause reasoning

Ullah et al. (2024) developed SecLLMHolmes to evaluate whether LLMs can identify and reason about software vulnerabilities. Their study examined eight models using 228 code scenarios covering eight vulnerability classes in C and Python. The evaluation considered more than whether a model selected the correct vulnerable or non-vulnerable label. It also examined consistency across repeated responses, the effect of different prompts, the faithfulness of explanations and the models' ability to handle changes to source code.

The findings are important because a correct vulnerability classification did not always mean that the model had identified the correct reason for the vulnerability. The authors also reported that model responses could change between runs and that seemingly minor changes to code, such as renaming variables or functions, could affect the results. This suggests that an evaluation based only on whether an LLM gives the correct final answer may overestimate its actual understanding. For the present research, the main implication is that root-cause explanations need to be assessed separately from the model's overall conclusion.

A more recent study by Du et al. (2026) investigated the ability of LLMs to distinguish vulnerable code from its patched version. The authors introduced PairVul, a dataset containing 586 vulnerable and patched function pairs collected from real-world CVEs. Their results showed that the evaluated models frequently failed to identify both members of a pair correctly. In 86%–94% of cases, the models did not correctly classify the vulnerable and patched versions together. The paper also found that prompt-based improvements were limited, while its Vul-RAG approach improved pairwise accuracy by 16–24 percentage points.

This work is closely related to the problem of understanding vulnerability fixes. It demonstrates that identifying a vulnerable code fragment is not enough; a model must also understand what changed and why the patched version no longer exhibits the same weakness. Nevertheless, PairVul evaluates vulnerability classification at function level. It does not, by itself, establish whether an agent's written root-cause explanation leads to a useful regression test. That distinction is relevant to the design of the current study.

## 2.3 Evaluating explanations produced by coding agents

Explanations are increasingly important as coding agents make changes across multiple files. Developers may rely on an agent's summary to understand what was changed and whether the change is appropriate. Pan et al. (2026) addressed this issue through ExplainBench, a benchmark for evaluating explanations generated by coding agents.

ExplainBench assesses whether an explanation accurately describes the intended behaviour of buggy code and the effect of a proposed patch. Its approach uses questions that an LLM should be able to answer when the explanation is informative and correct. The authors found that explanation quality is a separate evaluation dimension: the ranking of agents using ExplainBench differed from their ranking on SWE-bench Verified. They also observed cases in which agents claimed that a patch was correct when it was not.

ExplainBench supports the argument that an agent's explanation should not be treated as reliable simply because the agent completed a coding task. However, its focus is broader software-engineering explanations and patch effects, rather than the relationship between security root-cause explanations and generated security regression tests. It therefore provides a useful evaluation concept, but it does not answer the research question considered in this project.

The findings of Ullah et al. (2024) and Pan et al. (2026) point to a similar issue from different directions. A model can produce a correct-looking conclusion while its reasoning is incomplete or inaccurate. In security work, this matters because an incorrect explanation can lead a developer to test the wrong condition or apply an ineffective fix. An evaluation should therefore examine the technical claims made in an explanation, including whether the explanation identifies the relevant code, describes the triggering conditions and explains the security impact.

## 2.4 LLM-based regression-test generation

Regression tests are used to check that a defect does not return after a software change. LLMs offer a possible way to generate such tests from source code, issue descriptions or commit information. Liu et al. (2026) studied this problem in their FSE 2026 paper, *Evaluating LLM-based Regression Test Generation*. Their Cleverest prototype generated tests for 46 commits across projects including MuJS, Libxml2, Poppler, JerryScript, Z3 and PHP. The study considered programs such as parsers and interpreters, where inputs can be generated and executed to expose defects.

The authors reported that their feedback-directed approach could find bugs quickly and that generated inputs could also improve fuzzing when used as a seed corpus. The inclusion of PHP is especially relevant to the present project because it shows that LLM-based regression-test generation has already been investigated in the PHP ecosystem. Consequently, the general idea of asking an LLM to generate tests for PHP commits should not be presented as the main research contribution.

Cleverest focuses on generating inputs that exercise changed code and expose bugs. The current study has a different emphasis: it considers the accuracy of the agent's explanation of a security root cause alongside the effectiveness of the regression test it produces. The test is not judged only by whether it executes or finds a failure. It must distinguish the vulnerable implementation from the corrected implementation.

The quality of a generated test also depends on its expected result, often referred to as the test oracle. Molinelli et al. (2025) examined LLM-generated test oracles using 13,866 test oracles from 135 Java projects. Their dataset was selected so that the tests were created after the training cut-off dates of the evaluated models, reducing the risk that the results were influenced by memorisation of public examples. The generated oracles achieved an average mutation score of 43%, compared with 45% for human-designed oracles.

This result suggests that LLMs can produce useful test oracles in some settings, but it does not mean that all generated tests are reliable. The study was based on Java projects and mutation testing, rather than real-world security fixes in PHP. It nevertheless supports the use of measurable test effectiveness criteria instead of relying on a subjective judgement that a generated test looks reasonable.

## 2.5 Risks in evaluating generated tests

A test that runs successfully is not necessarily a useful regression test. It may fail to detect the original defect, or it may encode incorrect behaviour as the expected result. Charoosaei et al. (2026) investigated this problem in their study of LLM-generated regression tests. They analysed 145 pull requests from SciPy, Qiskit and pandas and distinguished between fault-revealing tests and fault-enforcing tests. Fault-revealing tests expose incorrect behaviour, while fault-enforcing tests preserve or assert behaviour that is itself faulty.

Their results show why test generation requires careful validation. Between 8% and 17% of generated tests were classified as fault-enforcing, while only 2.4%–4.8% revealed faults. The authors also found that many fault-enforcing tests continued to pass as the projects evolved. This indicates that generated tests can introduce a risk when their expected behaviour is accepted without checking it against the correct implementation.

For a security regression test, this issue can be addressed by executing the same test against both the vulnerable and patched versions. A useful test should expose the defect in the vulnerable version and pass when the corrected version is used. A test that passes on both versions does not demonstrate that it detects the vulnerability. A test that fails on both versions may be invalid or may be checking unrelated behaviour. A test that passes on the vulnerable version but fails on the patched version may be enforcing the faulty behaviour. These distinctions provide a practical basis for classifying test outcomes in the present study.

PatchBench, introduced by Shen et al. (2026), provides further support for validating software changes beyond a single proof-of-concept result. The benchmark examines AI agents performing vulnerability patching in C and C++ projects. The authors identify two problems with relying only on whether a supplied proof-of-concept input stops triggering a crash: an agent may reproduce a historical patch, or it may suppress the visible crash without correcting the underlying cause. Their evaluation found that proof-of-concept-only validation overestimated patching success by an average factor of 1.83. PatchBench therefore combines security validation with checks of semantic correctness.

Although PatchBench evaluates generated patches rather than the exact explanation-to-test relationship in this project, its findings are relevant to experimental design. A test should not be considered effective merely because it produces one expected failure. It should also be checked against the patched implementation and, where possible, against normal behaviour to reduce the chance of accepting a test that rejects valid functionality.

## 2.6 Security benchmarks and reproducible evaluation

Evaluating agents on real software is difficult because results depend on the repository, build environment, dependencies, test harness and vulnerability reproduction steps. Lee et al. (2025) introduced SEC-bench to address this issue. SEC-bench provides an automated framework for constructing software repositories and harnesses, reproducing vulnerabilities in isolated environments and evaluating agents on tasks such as proof-of-concept generation and vulnerability patching.

The authors reported maximum success rates of 18.0% for proof-of-concept generation and 34.0% for vulnerability patching on their complete dataset. These results demonstrate that real-world security tasks remain challenging for current agents. More importantly for this research, SEC-bench illustrates the value of isolated and reproducible environments. If the vulnerable and patched versions cannot be executed consistently, it becomes difficult to determine whether a generated test is genuinely detecting the defect.

A related concern is whether an agent has learned the answer from public material rather than independently analysing the supplied source code. Shen et al. (2026) identify patch memorisation as a threat to vulnerability-patching evaluations. Molinelli et al. (2025) also address possible benchmark contamination by using tests created after model training cut-off dates. These studies show that evaluation results should be interpreted in light of what information was available to the model. In the present study, the experimental procedure should therefore record the information supplied to each agent and avoid revealing the ground-truth patch before the initial explanation and test have been produced.

## 2.7 Reproducibility and variation between model responses

LLM outputs are not always identical when the same task is repeated. Ouyang et al. (2025) examined this issue using 829 code-generation problems from CodeContests, APPS and HumanEval. They found substantial variation between generated responses and reported that setting the temperature to zero did not guarantee identical outputs.

Ullah et al. (2024) also observed non-deterministic responses during security-vulnerability evaluation. Together, these findings indicate that a single response may not represent an agent's typical performance. If one model produces a strong explanation in one run and an inaccurate one in another, evaluating only one output could lead to an incomplete comparison.

For this reason, repeated trials and consistent experimental conditions are important. The model name and version, agent framework, prompt, tool access, generation settings and date of execution should be recorded. Repeated runs should use the same task information and execution environment. This will make it possible to report not only average performance but also variation between runs.

## 2.8 Synthesis and research gap

The reviewed studies establish several points. First, LLMs can identify vulnerabilities and generate code-related explanations, but their reasoning may be inaccurate, inconsistent or sensitive to small changes in the source code (Ullah et al., 2024; Du et al., 2026). Second, explanation quality is a meaningful evaluation dimension and should not be assumed from an agent's apparent task success (Pan et al., 2026). Third, LLM-based regression-test generation has already been studied, including in PHP projects (Liu et al., 2026). Fourth, generated tests require behavioural validation because they may fail to reveal a defect or may preserve faulty behaviour (Molinelli et al., 2025; Charoosaei et al., 2026). Finally, real-world security evaluations need reproducible environments and validation that goes beyond a single proof-of-concept check (Lee et al., 2025; Shen et al., 2026).

These studies provide a strong foundation, but they examine different parts of the problem. Research on vulnerability reasoning measures whether models identify and explain security weaknesses. Research on code explanations measures whether explanations accurately describe code behaviour or changes. Research on test generation evaluates whether generated tests expose defects or provide useful test oracles. Security-agent benchmarks examine practical performance on vulnerability-related tasks. Based on the literature reviewed for this study, there remains a specific question worth investigating: **whether the accuracy of an AI coding agent's source-grounded explanation of a real-world security vulnerability is associated with the effectiveness of the regression test generated by that same agent.**

This gap is narrower than claiming that AI-generated security tests or vulnerability explanations have not been studied before. Both areas have existing research, and PHP has already appeared in regression-test-generation experiments. The proposed contribution is to evaluate the two outputs together under the same controlled conditions. The explanation can be assessed against the source code and the verified vulnerability behaviour, while the generated test can be executed against vulnerable and patched versions. The results can then be analysed to determine whether more accurate explanations tend to accompany more effective tests.

The initial PHP2Shell case study provides a starting point for developing this evaluation process. However, a single case is not sufficient to support broad conclusions about AI coding agents. The experimental dataset will need multiple suitable security fixes, with clear vulnerable and patched versions and a reproducible way to execute tests. The scope and number of cases should be finalised in the methodology chapter after assessing the availability and feasibility of suitable cases.

## 2.9 Chapter summary

Previous research shows that LLM-based security analysis, code explanation and regression-test generation each have important limitations. Correct classification does not guarantee correct reasoning, and generated tests can be ineffective or even preserve faulty behaviour. Existing benchmarks provide useful methods for evaluating these capabilities, but they do not remove the need to validate outputs against real vulnerable and patched software.

This study will build on that work by examining root-cause explanation accuracy and security regression-test effectiveness together. Rather than treating an agent's explanation or generated test as correct based on its wording or appearance, both will be assessed using source-level evidence and execution results. This provides the basis for the research questions and experimental procedure developed in the following chapter.
